# P1 · Core 抽象与内存模型

> 阶段：P1（core 类型完备）
> 状态：✅ 已落地并验证
> 前置：[`P0.md`](./P0.md)

---

## 1. 范围

P1 把 P0 的骨架补成一套**可被算子与后端稳定依赖的核心抽象**。本文解释每个 core 类型的精确契约，以及三件最容易出错的事：

1. `Tensor` 是描述符，`Buffer` 才持有内存——视图为什么零拷贝；
2. `Context::Copy` 如何按 host/device 选路径，以及同步契约；
3. `Tensor` 为什么可以比 `Context` 活得久，以及 `Wrap` 如何零拷贝接管外部内存。

core 层位于 `include/mycv/core/` 与 `src/core/`，**不依赖任何第三方头**（见 [`P0.md`](./P0.md) §3.4）。

---

## 2. Shape：固定容量，热路径零堆分配

| 项 | 契约 |
| --- | --- |
| 最大维度 | `Shape::kMaxDims = 8`（[shape.h](../../include/mycv/core/shape.h#L18)） |
| 存储 | `std::array<int64_t, 8> dims_` + `int rank_`，**无堆分配** |
| 构造 | 不校验；超过 8 维被截断（`Shape` 在内核里要保持廉价） |
| 语义校验 | `Shape::Validate()`：所有 dim 必须为正，否则 `kInvalidArgument` |
| 标量 | rank 0 的 `Numel() == 1` |

> 设计意图：`Shape` 是值类型，按值传递、在内核中频繁构造。把它做成固定容量，避免每次算子调用都触发 `std::vector` 堆分配。语义校验（dims 为正）推迟到 `Validate()`，由 `Context::AllocateTensor` / `Wrap` 在边界调用，内核内部不再重复校验。

## 3. Tensor：描述符 + 共享 Buffer

`Tensor` 的全部状态（[tensor.h](../../include/mycv/core/tensor.h#L91-L101)）：

```
buffer_   : shared_ptr<Buffer>   // 内存持有者（可被多个视图共享）
owner_    : weak_ptr<Backend>    // 分配该 Buffer 的后端（用于 Clone/Copy 解析）
shape_    : Shape
dtype_    : DataType
strides_  : array<int64_t, 8>    // 单位：元素，不是字节
offset_   : size_t               // 元素起点偏移（单位：元素）
device_   : Device
backend_  : BackendType
```

**关键性质**：

- `Tensor::data()` 返回 `buffer_->data() + offset_`（按字节），即**带偏移的指针**；视图通过修改 `offset_` 与 `strides_` 指向同一块内存的不同区域，不拷贝元素。
- `Tensor` 可拷贝/可赋值，代价只是 `shared_ptr` 引用计数 +1（`Buffer` 不可拷贝，[memory.h](../../include/mycv/core/memory.h#L45-L46)）。
- `backend()` / `device()` 描述这个张量的数据所在位置，是算子分发与拷贝路径选择的依据。
- `owning_backend()` 返回 `weak_ptr`：`Clone` / 跨后端拷贝需要"当初分配这块内存的后端"，但 `Context` 可能已经析构，故用弱引用避免悬垂（详见 §8）。

## 4. Buffer 与 MemoryManager：把"怎么释放"藏进 deleter

### 4.1 Buffer

`Buffer` 是一个**不透明、设备无关**的内存句柄（[memory.h](../../include/mycv/core/memory.h#L30-L60)）：

| 字段 | 含义 |
| --- | --- |
| `data_` | 原始指针（host 或 device，调用方按 `kind` 解释） |
| `bytes_` | 字节数 |
| `device_` | 所在设备 |
| `kind_` | `kHost` / `kHostPinned` / `kDevice` |
| `deleter_` | `std::function<void(void*, size_t)>`，由后端注入 |

析构时若 `deleter_` 非空且 `data_ != nullptr`，则调用 deleter 释放。**`Buffer` 本身非虚、轻量**；分配与释放策略完全由后端决定（`posix_memalign` / `cv::Mat` / `cudaMalloc` / NPU 池等）。这是"core 零第三方依赖"的关键——`Buffer` 不知道也不关心内存来自哪里。

### 4.2 MemoryKind

`MemoryKind`（[memory.h](../../include/mycv/core/memory.h#L15-L19)）区分内存物理属性，供 `Context::Copy` 选路径：

- `kHost`：普通可分页 host 内存；
- `kHostPinned`：锁页内存（DMA 友好，未来 H2D 优化用）；
- `kDevice`：设备内存（GPU / NPU）。

### 4.3 MemoryManager

统一的后端分配接口（[memory.h](../../include/mycv/core/memory.h#L64-L81)）：

```cpp
virtual Result<std::shared_ptr<Buffer>> Allocate(size_t bytes, size_t alignment = 64) = 0;
virtual Status Copy(Buffer* dst, size_t dst_off, const Buffer* src, size_t src_off,
                    size_t bytes, Stream* stream = nullptr) = 0;
virtual MemoryStats Stats() const = 0;
```

`MemoryStats` 暴露 `allocated_bytes` / `peak_bytes` / `allocation_count`。**池里缓存的空闲块不计入活跃分配**——`allocated_bytes` 是"当前被 Tensor 持有的字节"，不是"向 OS 申请的总量"。这一点对基准测试的峰值采样很重要（CPU 内存设计的细节见 [`../qa/cpubackends.md`](../qa/cpubackends.md)）。

## 5. Stream：执行流抽象

```cpp
class Stream {
  virtual Device device() const = 0;
  virtual Status Synchronize() = 0;
  virtual bool synchronous() const { return true; }  // 默认同步
};
```

- CPU 后端的 stream 是同步的（`synchronous() == true`），`Synchronize()` 为空操作。
- CUDA / NPU 后端包装原生队列，`synchronous() == false`；`Synchronize()` 阻塞直到队列中所有操作完成。

`Stream` 的存在让算子内核可以把工作提交到指定流，而 core 不感知底层是 CPU 还是 GPU。当前公开算子在返回前同步（见 [`P5.md`](./P5.md) §7），所以默认 `OpContext.stream == nullptr` 表示"用 Context 的默认流"。

## 6. Device 与 Backend：刻意分离

这是 P0 决策 D2 的落地。两者**不是一回事**：

| 概念 | 枚举 | 例子 |
| --- | --- | --- |
| 后端（实现提供者） | `BackendType` | `kNativeCpu` / `kOpenCV` / `kCUDA` / `kNPU` |
| 设备（硬件） | `DeviceType` + `index` | `cpu:0` / `gpu:0` / `npu:0` |

`DefaultDeviceType(BackendType)` 只做静态映射（[device.h](../../include/mycv/core/device.h#L44-L55)）：`native_cpu` 与 `opencv` 都落在 `kCPU`，`cuda` 落在 `kGPU`。

> 为什么分开：OpenCV 是"跑在 CPU 上的一个实现"，CUDA 是"跑在 GPU 上的一个实现"。如果把后端等同于设备，调度层就会写死"OpenCV ⇒ CPU"，未来出现"CPU 上的另一个后端"或"GPU 上的另一个后端"时就要改 core。分离后，`BackendType` 只用于算子分发表的键，`Device` 只用于拷贝路径与设备匹配。

## 7. Context：统一入口

`Context` 绑定**一个 Backend + 一个 Device**，暴露统一的分配/调度/拷贝入口（[context.h](../../include/mycv/core/context.h)）：

```cpp
static Result<std::shared_ptr<Context>> Create(BackendType, int device_index = 0);
Result<Tensor> AllocateTensor(const Shape&, DataType, size_t alignment = 64);
Result<Tensor> Wrap(void* data, const Shape&, DataType,
                    MemoryKind kind = MemoryKind::kHost, Buffer::Deleter = nullptr);
Status Copy(Tensor* dst, const Tensor& src, Stream* stream = nullptr);
Status Synchronize();
MemoryManager& memory();
Stream& stream();
```

- `Create` **不做自动探测**：后端不存在返回 `kUnsupported`。
- `AllocateTensor` 委托给 `Tensor::Create`，后者调用后端的 `MemoryManager::Allocate` 并组装一个**连续** Tensor（row-major strides）。
- `Copy` 见 §9。
- `Wrap` 见 §10。

## 8. 视图族：零拷贝元数据操作

`Tensor` 提供一组只改描述符、不拷贝元素的操作（[tensor.h](../../include/mycv/core/tensor.h#L70-L77)）：

| 操作 | 语义 | 是否拷贝 |
| --- | --- | --- |
| `View(shape)` | 重新解释形状，要求 `Numel` 不变 | 否，共享 Buffer |
| `Slice(dim, begin, end)` | 沿某维切一段，调整 `offset_` 与该维 stride | 否，共享 Buffer |
| `Permute(order)` | 重排维度，重算 `strides_` | 否，共享 Buffer |
| `Reshape(shape)` | 连续则零拷贝（等价 View）；**非连续则 Clone 深拷贝** | 视情况 |
| `Clone()` | 分配新 Buffer 并逐元素深拷贝 | 是 |

**两条不变量**：

1. 视图共享整块底层 `Buffer`——`Slice` 出一个小片段，整块内存仍存活，无法只释放片段（这是"轻量视图"换"简单所有权"的取舍，见 [`P0.md`](./P0.md) §9）。
2. `Reshape` 绝不静默失败：能零拷贝就零拷贝，不能就显式深拷贝，调用方拿到的永远是有效张量。

> 非连续视图（如 `Slice` 后）能否参与算子与拷贝？可以。`Context::Copy` 按 stride 逐元素搬运（[`../qa`](../qa/) 有专文）；元素级内核通过 `TensorIterator` 按 stride 遍历。算子对连续性的要求在校验层显式声明（见 [`P2.md`](./P2.md)）。

## 9. Context::Copy：跨后端统一拷贝

`Context::Copy(dst, src)` 拷贝**逻辑元素**（不是裸字节），因此能处理非连续视图。路径由 `dst` 与 `src` 的 `MemoryKind` / `Device` 决定：

| 场景 | 路径 |
| --- | --- |
| host ↔ host（含 native_cpu ↔ opencv） | 直接 `memcpy` 或按 stride 逐元素拷贝 |
| host → device（H2D） | 目标后端的 `CopyBuffer`（CUDA：`cudaMemcpyAsync`） |
| device → host（D2H） | 同上反向 |
| device → device（D2D，同设备） | 设备内拷贝 |
| 跨不同 GPU（peer-to-peer） | **返回 `kUnsupported`**，不偷偷经 host 中转 |

**同步契约**：`Copy` 在返回前完成同步（CUDA 路径会 `cudaStreamSynchronize`），即返回后 `dst` 立即可读。这是当前的公开契约；若未来引入异步拷贝，需另行定义，不得隐式改变现有语义。

> 选路原则：**由目标上下文决定路径**，且后端"碰不到某类内存"时必须返回 `kUnsupported`，而不是在调用方背后经 host  staging。这样新增后端只需实现 `Backend::CopyBuffer` 即可参与拷贝。

## 10. 生命周期：Tensor 可以比 Context 长寿

这是 P1 最重要的正确性保证，也是最容易写出悬垂指针的地方。

**场景**：

```cpp
Result<Tensor> MakeFoo() {
  auto ctx = Context::Create(BackendType::kCUDA).value();
  return ctx->AllocateTensor(...);   // ctx 即将析构
}
// 这里使用返回的 Tensor 必须仍然安全
```

**机制**：

- `Tensor::owner_` 是 `std::weak_ptr<Backend>`，不延长 Context 寿命。
- 但 `Buffer` 的 deleter 捕获的不是 `Backend*`，而是后端内部的 **`shared_ptr<AllocatorState>`**（CPU / CUDA 内存池的共享状态）。
- 因此：`Context` 析构 → `Backend` 析构 → 但其 `AllocatorState` 仍被活着的 `Buffer` 引用 → 最后一个 `Buffer` 释放时，deleter 把内存（或整池）正确还给 OS/驱动。

一句话：**`Context` 死了，分配它的"策略"消失了，但已分配内存的"回收责任"随 `Buffer` 延续。** `Clone` / 跨后端拷贝在 `owner_` 已过期时，会创建一个临时后端兜底（现有行为），保证"tensor 比 context 长寿"不触发 use-after-free。

> 详见 [`../qa/cpubackends.md`](../qa/cpubackends.md)（CPU 侧机制）与 [`../qa/memory_lifecycle.md`](../qa/memory_lifecycle.md)（通用模型）。ASAN/UBSAN 构建（`build-asan/`，10/10 通过）专门覆盖这条路径。

## 11. Wrap：零拷贝接管外部内存

`Context::Wrap` 是 P1 后追加的能力（[context.h](../../include/mycv/core/context.h#L44-L51)）：把**另一个运行时已分配的内存**（`cv::Mat`、`cudaMalloc`、NPU 缓冲……）包装成 `Tensor`，**不分配、不拷贝**。

```cpp
auto t = ctx->Wrap(external_ptr, shape, dtype, MemoryKind::kDevice,
                   [](void* p, size_t) { cudaFree(p); });
```

**两种语义，由 deleter 决定**：

| deleter | 语义 | 释放责任 |
| --- | --- | --- |
| 空（`nullptr`） | **借用（borrow）** | 调用方保持内存存活；`Tensor` 析构不释放 |
| 非空 | **收养（adopt）** | 最后一个 `Tensor`/`Buffer` 引用死亡时调用 deleter 释放 |

**保证**：

- `tensor.data() == external_ptr`（零拷贝：同一指针）；
- 不经过 `MemoryManager::Allocate`，故 `MemoryStats` 不变（外部内存不算管理器分配）；
- 包装出的 `Tensor` 设置 `owner_ = backend_`，可直接作为同上下文算子的输入（`device()`/`backend()` 匹配，通过校验）。

**调用方责任（重要）**：当外部内存是在**另一条流**上产生的（例如外部 `cudaMemcpy` 在默认流、mycv 用 non-blocking 流），数据对 mycv 的内核未必立即可见。**调用方必须先同步**（`cudaDeviceSynchronize` 或事件等待）再把指针交给 `Wrap`/算子。库不替你做这个同步，因为它不知道外部流的存在。这是刚踩过并写进测试的坑，详见 [`../qa/cuda_stream_visibility.md`](../qa/cuda_stream_visibility.md)。

## 12. 验收与边界

P1 完成的判据（已实测）：

- `View` / `Slice` / `Cast` / 跨后端拷贝测试全绿；
- ASAN/UBSAN（`build-asan/`）下全部测试通过，包括"Tensor 比 Context 长寿"用例；
- 非连续输入（slice 后）能正确参与 `Context::Copy`；
- `Wrap` 借用/收养两种语义、零分配、作为算子输入均通过测试（CPU + CUDA）。

**core API 冻结**：P1 之后 core 只允许**追加**接口，不允许修改已有签名，以便 P2–P5 并行开工。
