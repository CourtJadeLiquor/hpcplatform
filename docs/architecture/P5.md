# P5 · CUDA 后端

> 阶段：P5（CUDA 后端）
> 状态：✅ 已落地并验证（RTX 4060 Ti / sm_89，CUDA 13.5）
> 前置：[`P1.md`](./P1.md)、[`P2.md`](./P2.md)

---

## 1. 定位

CUDA 是 `BackendType::kCUDA`——GPU 上的后端实现。它提供设备内存管理、异步流、跨设备拷贝与 8 个算子的 GPU 内核，让同一条预处理链路可以在 GPU 上跑，且与 CPU / OpenCV 结果可对拍。

代码位于 `src/backends/cuda/`，core 层不 `#include` 任何 CUDA 头。测试需要 GPU，无 GPU 时输出 SKIP 但 `ctest` 仍全绿。

---

## 2. 编译开关与硬性前提

```cmake
option(MYCV_WITH_CUDA OFF)
```

开启时：

- `enable_language(CUDA)` + `find_package(CUDAToolkit)`；
- **必须显式传入 `CMAKE_CUDA_ARCHITECTURES`**（本机验证值 `89`，对应 RTX 4060 Ti 的 compute capability 8.9）；
- 定义宏 `MYCV_WITH_CUDA`，CUDA 内核注册进分发表。

> 为什么强制显式架构：不指定时 CMake/nvcc 可能用默认或探测值，导致生成的 SASS 与目标卡不匹配（运行时 `no kernel image is available`）。显式指定让构建可复现。

关闭时默认构建（`build-default/`）与测试不受影响；ASAN 构建（`build-asan/`）也不编 CUDA（CUDA 与 sanitizer 不兼容），只覆盖 CPU + OpenCV。

---

## 3. 内存：cudaMalloc/cudaFree + 缓存池

`CudaMemoryManager`：

- 分配走 `cudaMalloc`，释放走 `cudaFree`；
- 维护一个**按精确字节匹配的空闲块缓存池**，释放的块入池、下一次同尺寸分配直接命中，避免反复 `cudaMalloc/cudaFree`（这是基准 `cache_reuse=yes` 的来源，与 CPU 池语义一致）；
- 统计与 CPU/OpenCV 对齐：`allocated_bytes` / `peak_bytes` / `allocation_count`，**池中的缓存块不计入活跃分配**；
- 池状态用 `shared_ptr` 与 `Buffer` 共享，保证 `Context` 析构后已分配的 device 内存仍能正确释放（[`P1.md`](./P1.md) §10）。

---

## 4. 流：non-blocking + 同步原语

`CudaStream` 包装一条 CUDA 流，创建时带 `cudaStreamNonBlocking` 标志（[cuda_stream.cpp](../../src/backends/cuda/cuda_stream.cpp)）。性质：

- `synchronous() == false`；
- `Synchronize()` 阻塞直到该流所有操作完成；
- 流与默认（NULL）流**不隐式同步**——这是 §7 外部内存可见性问题的根源。

---

## 5. 跨设备拷贝

`Context::Copy` 覆盖以下路径（[`P1.md`](./P1.md) §9）：

| 路径 | 实现 |
| --- | --- |
| H2D（host → device） | `cudaMemcpyAsync` 到流，再同步 |
| D2H（device → host） | 同上反向 |
| D2D（同设备内） | 设备内拷贝 |
| 跨不同 GPU（peer-to-peer） | **返回 `kUnsupported`**，不经 host 偷偷中转 |

选路原则与其他后端一致：碰不到的内存返回 `kUnsupported`，不在调用方背后 staging。

---

## 6. 算子内核

8 个算子全部有 CUDA 实现，集中在 `src/backends/cuda/cuda_kernels.cu`：

- 元素级：`Add` / `Mul` / `Cast` / `Normalize`；
- 图像：`Resize` / `Crop` / `Transpose` / `WarpAffine`。

CUDA 错误统一经 `CudaStatus` 包装成 `Status`。**layout 约束与 OpenCV 一致**：图像算子只承诺 `HW`/`HWC`/`NHWC`，NCHW 明确拒绝，由调用方显式 `Transpose`。

内核读取输入张量的 `device` 指针，因此 `Wrap` 进来的外部 device 指针可直接作为输入（[`P1.md`](./P1.md) §11），前提是数据已对该流可见（见 §7）。

---

## 7. 同步契约：公开算子返回前同步

当前契约：**每次公开算子调用在返回前同步**（内核 launch 后调用 `cudaStreamSynchronize`）。这意味着：

- 算子返回的 `Tensor` 立即可读、可立即 `Copy` 回 host；
- 输出张量的生命周期简单——不需要"等流完成再释放"的复杂约定；
- 代价是无法在 host 侧重叠多个算子（无流水线重叠）。

> 这是一个**显式的当前契约**，不是永久限制。若未来需要异步流水，必须新增显式异步入口并定义输出生命周期/同步契约，**不得隐式改变现有同步语义**（[`P0.md`](./P0.md) §7 扩展契约第 6 条）。

---

## 8. 外部内存的可见性（重要，刚踩过的坑）

`Context::Wrap` 可以把外部运行时分配的 device 内存（`cudaMalloc`、`cv::cuda::GpuMat`、NPU 映射等）零拷贝接入。但有一条**调用方责任**：

> mycv 的 CUDA 流是 `cudaStreamNonBlocking`，与默认流不隐式同步。如果外部数据是在**另一条流**（或默认流）上产生的，在数据对 mycv 的流可见之前，内核可能读到旧值/未初始化值。

**正确做法**：把外部内存交给 `Wrap` / 算子之前，调用方必须先同步——`cudaDeviceSynchronize()`、或在外部流记录事件让 mycv 流等待。库**不替你做**这个同步，因为它不知道外部流的存在。

这条规则已写进 CUDA 测试 `CudaWrapAdoptsExternalDeviceMemory`（`tests/consistency/test_cuda_backend.cpp`）：测试用裸 `cudaMemcpy`（默认流）填充外部 device 指针后，先 `cudaDeviceSynchronize()`，再 `Wrap` 并喂给 GPU `Add`，验证零拷贝输入路径正确且 deleter（`cudaFree`）在最后引用释放时触发。详见 [`../qa/cuda_stream_visibility.md`](../qa/cuda_stream_visibility.md)。

## 9. 测试：按设备可用性跳过

`test_cuda_backend` 在无 GPU 时：

```cpp
auto cuda_result = Context::Create(BackendType::kCUDA);
if (!cuda_result.ok()) { std::cout << "SKIP ...\n"; return; }
```

即 `Context::Create(kCUDA)` 失败（无驱动/无设备）时输出 SKIP 原因并返回，`ctest` 仍计为通过。这样默认构建与无 GPU 的 CI 不会因缺少硬件而红。

---

## 10. 两个硬约束

1. **只接受 `kNaive`**：`cpu_level != kNaive` 返回 `kInvalidArgument`（与 OpenCV 同理）。
2. **公开算子同步返回**：见 §7，当前不提供异步入口。

---

## 11. 验收

- GPU 可用机器上：8 个算子与 CPU naive 按跨后端容差对拍通过；H2D→kernel→D2H 往返及完整预处理流水线正确。
- 默认（无 CUDA）构建 9/9 测试通过；无 GPU 时 CUDA 测试输出 SKIP 原因。
- `Wrap` 外部 device 内存作为零拷贝输入的路径通过；deleter 正确触发。
- 三棵构建树（`build` / `build-default` / `build-asan`）ctest 全绿。

---

## 12. 局限（已知）

- 仅单 GPU；多 GPU peer-to-peer 拷贝返回 `kUnsupported`。
- 公开算子同步返回，无 host 侧流水线重叠。
- 外部内存的流可见性由调用方负责（§8）。
- 必须显式指定 `CMAKE_CUDA_ARCHITECTURES`。
