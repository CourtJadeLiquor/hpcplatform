# P4 · OpenCV 后端

> 阶段：P4（OpenCV 后端）
> 状态：✅ 已落地并验证
> 前置：[`P1.md`](./P1.md)、[`P2.md`](./P2.md)

---

## 1. 定位

OpenCV 是 `BackendType::kOpenCV`——**CPU 上的一个后端实现**，不是库的依赖本体。它的价值是让 mycv 的预处理链路可以直接复用 OpenCV 高度优化的 `imgproc` 内核，同时保持与原生 CPU / CUDA 后端**统一的 API 与对拍能力**。

后端代码位于 `src/backends/opencv/`，core 层不 `#include` 任何 OpenCV 头（[`P0.md`](./P0.md) §3.4）。

---

## 2. 编译开关：关闭时零影响

```cmake
option(MYCV_WITH_OPENCV OFF)
```

开启时 `find_package(OpenCV 4 REQUIRED COMPONENTS core imgproc)`，并定义宏 `MYCV_WITH_OPENCV`，使 OpenCV 内核注册进分发表（[`P2.md`](./P2.md) §4.2）。

**关闭时**：不找 OpenCV、不编 OpenCV 后端、默认构建与所有测试不受影响（`build-default/` 9/9 通过即验证此点）。这是"后端可替换"的硬指标——第三方依赖的有无不能波及核心。

---

## 3. 内存模型：Buffer 持有 cv::Mat

`OpenCvMemoryManager` 的核心设计（对应 P0 决策 D4）：

- 分配时创建一个 `cv::Mat`，把它的 `data` 指针作为 `Buffer::data_`；
- `Buffer` 的 deleter 捕获一个 **shared 持有 `cv::Mat`** 的对象，`~Buffer` 时让 `cv::Mat` 随引用计数自然释放；
- 因此 `Tensor` 与底层 `cv::Mat` **同生命周期**，不存在"Tensor 还在用、Mat 已被外部释放"的悬垂。

> 为什么不让 `cv::Mat` 逃逸给调用方：`cv::Mat` 是引用计数头，裸指针 `data` 一旦脱离 Mat 的生命周期管理就会悬垂或双重释放。把 Mat 独占在 Buffer 的 deleter 闭包里，调用方只拿到 `Tensor`，所有权边界清晰。ASAN 构建覆盖此路径。

统计与 CPU/CUDA 对齐：`MemoryStats` 给出活跃 `allocated_bytes` / `peak_bytes` / `allocation_count`；同一 Context 内多次分配/释放后归零。

## 4. dtype 与 layout 约束：写死支持矩阵，不满足就报错

OpenCV 的 `cv::Mat` 与 `imgproc` 对类型和布局有明确限制。后端**不做隐式转换**，而是把支持矩阵写死并在不满足时返回错误：

### 4.1 dtype 支持

| dtype | 支持 |
| --- | --- |
| `kUInt8` / `kFloat32` / `kFloat64` | ✅ |
| `kFloat16` 及其他 | `kUnsupported` |

> `f16` 在 OpenCV 4 中支持有限且布局语义易混淆，明确拒绝，由调用方决定是否先 `Cast`。

### 4.2 layout 支持

| 布局 | 支持 |
| --- | --- |
| `HW`、`HWC`、`NHWC` | ✅ |
| `NCHW` | 明确拒绝（返回错误） |

> 为什么拒绝 NCHW：`cv::Mat` 不支持任意 stride 的 NCHW 视图。**需要 NCHW 时由调用方显式 `Transpose` 先转布局**，而不是后端偷偷转换——偷转既会引入隐藏拷贝，也会让"我以为零拷贝其实拷贝了"的性能结论失真。这条规则同样适用于 CUDA 后端的图像算子（见 [`P5.md`](./P5.md)）。

---

## 5. 算子映射

OpenCV 后端把算子映射到 `cv::imgproc` / `cv::Mat` 操作：

| mycv 算子 | OpenCV 实现 |
| --- | --- |
| `Add` | `cv::add` |
| `Mul` | `cv::multiply` |
| `Cast` | `cv::Mat::convertTo`（整数保持截断，与 CPU 精确一致） |
| `Normalize` | `split` + `convertTo` 组合实现逐通道均值方差 |
| `Resize` | `cv::resize` |
| `Crop` | `cv::Mat` ROI（零拷贝视图） |
| `Transpose` | `cv::transpose` |
| `WarpAffine` | `cv::warpAffine` |

`Normalize` 不用单一 OpenCV 调用，而是组合 `split` + `convertTo`，以保证与 CPU/CUDA 的通道语义一致。

---

## 6. 两个硬约束

1. **只接受 `kNaive`**：`OpContext.cpu_level != kNaive` 时返回 `kInvalidArgument`。OpenCV 后端没有"多版本"语义，传 `kOpenMP` 等于参数错误（[`P2.md`](./P2.md) §5 口诀：参数错 → `kInvalidArgument`）。
2. **不静默转换 dtype/layout**：见 §4，不满足即报错。

---

## 7. 互拷：native_cpu ↔ opencv

两者都是 host 内存（`MemoryKind::kHost`），`Context::Copy` 走直接 `memcpy` 路径（同设备 host↔host）。因此：

- 同形状连续张量：一次 `memcpy`；
- 非连续视图：按 stride 逐元素搬运（`Context::Copy` 拷贝逻辑元素，见 [`P1.md`](./P1.md) §9）。

> 注意：`cv::Mat` 可能有自身的 stride（对齐填充）。互拷时按 mycv Tensor 的 `ByteSize`/stride 精确搬运，不假设 `cv::Mat` 连续。

---

## 8. 验收

- 未安装 OpenCV 时默认构建与全部测试不受影响。
- 开启后 `ctest` 全绿；native vs OpenCV 按跨后端容差对拍通过，整数 Cast 截断精确一致。
- 同一 Context 多次分配/释放后 `MemoryStats` 归零。
- 请求 `kFloat16` / NCHW / 非 naive level 时返回确定错误码，不静默降级。

---

## 9. 局限（已知）

- 仅支持 OpenCV 4；`core` + `imgproc` 组件。
- dtype 与 layout 支持矩阵窄于原生 CPU（这是刻意的边界，不是缺陷）。
- `cv::Mat` 所有权独占在 Buffer 内，调用方无法直接拿到 `cv::Mat`（若需互操作，走 `Context::Copy` 或 `Wrap`）。
